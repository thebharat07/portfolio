Keys of the All-Father:
Exposed API Key in S3-Hosted JS

An API key hardcoded in a publicly accessible JavaScript file on Amazon S3 — and a troll flag that pointed us to the real endpoint hiding in plain sight.

TL;DR

A static website hosted on Amazon S3 loaded a JavaScript file containing a hardcoded API key and endpoint URL. Calling the endpoint with the key returned a troll flag — but switching from /v1/ to /v2/internal/flag (already in the JS source) returned the real flag.

Challenge Description

The challenge lore read:

"A service within the realms relies on hidden keys to grant access to its deeper knowledge. These keys are not meant to be seen, yet sometimes they are left where curious eyes may find them. Systems trust that what is hidden will remain hidden... but that is not always the case. Look closely at how access is granted. You may already have everything you need."

The challenge gave us a URL to a static website. The hint "you may already have everything you need" was the key — everything required to solve it was already on the page.

Step 1 — Source Code Inspection

The first thing to do with any web challenge is view the page source. We opened the page and immediately noticed it was served from Amazon S3 — visible from the response headers:

http response headers 
HTTP/1.1 200 OK
Server: AmazonS3
x-amz-request-id: N83TSAVNFHPM1E2N
Content-Type: text/html
Last-Modified: Sat, 21 Mar 2026 09:28:21 GMT
☁️  Hosted on Amazon S3 — static files are publicly accessible via HTTP

The HTML source contained a script tag loading a JavaScript file from S3. We fetched it directly:

bash 
curl https://zw20ng1w0m.execute-api.ap-south-1.amazonaws.com/static/app.js

The JavaScript file contained the following code:

javascript — app.js (served from S3) 
const API_URL = "https://zw20ng1w0m.execute-api.ap-south-1.amazonaws.com/v2/internal/flag";

async function getFlag() {
    const out = document.getElementById("output");
    out.textContent = "⏳ Sending request…";
    try {
        const res = await fetch(API_URL, {
            method: "GET",
            headers: {
                "x-api-key": "my-super-secret-api-key-12345"
            }
        });
        const data = await res.json();
        out.textContent = JSON.stringify(data, null, 2);
    } catch (err) {
        out.textContent = "❌ Error: " + err;
    }
}
⚡ Critical Discovery

Two secrets hardcoded in plain JavaScript — an API endpoint URL and an API key — both completely visible to anyone who views the page source. This is one of the most common real-world vulnerabilities.

The extracted credentials were:

extracted secrets 
API_URL = "https://zw20ng1w0m.execute-api.ap-south-1.amazonaws.com/v2/internal/flag"
API_KEY = "my-super-secret-api-key-12345"

Step 2 — Call the API with the Extracted Key

We directly called the API endpoint using the hardcoded key in the x-api-key header:

bash 
curl -H "x-api-key: my-super-secret-api-key-12345" \
  https://zw20ng1w0m.execute-api.ap-south-1.amazonaws.com/v2/internal/flag

Response:

json 
{"flag": "REDFOX{ALMOST_THERE_JUST_NOT_HERE}"}

A troll flag! The challenge was telling us we were close but needed to look harder. The endpoint was right, the key was right — but this was a decoy response designed to mislead.

Step 3 — Analyzing the API URL Structure

We looked more carefully at the URL structure. The endpoint was:

https://zw20ng1w0m.execute-api.ap-south-1.amazonaws.com/v2/internal/flag
execute-api.amazonaws.com → AWS API Gateway endpoint
/v2 → API version 2 (the one in the JS source)
/internal → restricted internal path
/flag → the flag endpoint

The JS source already had /v2/internal/flag — but returning a troll flag suggested there might be other versions or paths. We tried /v1/ — the older version that was perhaps less protected:

bash 
# Try version 1 of the API
curl -H "x-api-key: my-super-secret-api-key-12345" \
  https://zw20ng1w0m.execute-api.ap-south-1.amazonaws.com/v1/internal/flag

Response:

json 
{"flag": "REDFOX{*********}"}

Why This Happens in the Real World

This is not just a CTF scenario — exposed API keys in client-side JavaScript are one of the most common and most impactful real-world vulnerabilities. Here's why it keeps happening:

REASON_01
Development convenience
Developers hardcode keys during development for convenience and forget to remove them before deployment.
REASON_02
Misunderstanding of "hidden"
Teams assume minified or bundled JS is hard to read — but deobfuscation tools make it trivial to extract strings.
REASON_03
S3 public access
Static assets on S3 are publicly accessible by design — there is no concept of "server-side only" for S3-hosted files.
REASON_04
Old API versions
API v1 was never decommissioned when v2 was deployed — old endpoints often have weaker protection or are forgotten entirely.

Vulnerabilities & Fixes

1. API Key Hardcoded in Client-Side JavaScript

The most fundamental mistake. Any secret placed in JavaScript that runs in the browser is accessible to anyone. Period. Minification, obfuscation, and bundling offer zero real protection — all of it can be reversed.

Fix: API keys must live server-side only. The browser should call your own backend, which then calls the third-party API with the key. The key never touches the client. Use environment variables on the server — never in frontend build output.

architecture — correct approach 
// ❌ WRONG: key in frontend JS (visible to everyone)
const res = await fetch(EXTERNAL_API, {
  headers: { 'x-api-key': 'my-super-secret-api-key-12345' }
});

// ✅ CORRECT: browser calls YOUR backend proxy
const res = await fetch('/api/proxy/flag');
// Your backend (Node/Python/etc) adds the secret header:
// fetch(EXTERNAL_API, { headers: { 'x-api-key': process.env.API_KEY } })

2. Static Files Hosted on Public S3

S3-hosted static websites are entirely public. Every file — HTML, CSS, JavaScript, images — is readable by anyone on the internet. There is no authentication layer for static S3 hosting.

Fix: Never store sensitive configuration or secrets in S3-hosted static files. Use CloudFront with signed URLs if you need access control. Treat every S3 static file as completely public regardless of what it contains.

3. Undeprecated API Versions

The v1 API endpoint was still active and accepting the same key as v2. Old API versions are frequently forgotten, less monitored, and may have weaker access controls than newer versions.

Fix: Decommission old API versions properly. Use API Gateway usage plans and stages to enforce which versions are active. Set sunset dates and return deprecation headers before retiring versions. Monitor all active endpoints equally.

4. No Rate Limiting or Key Scoping

The API key worked on all endpoints with no restriction. A properly scoped key would only grant access to the specific resources it needs — not all internal endpoints.

Fix: Apply the principle of least privilege to API keys. Scope keys to specific endpoints, HTTP methods, and IP ranges where possible. Implement rate limiting on all API Gateway endpoints. Rotate keys regularly and monitor usage for anomalies.
